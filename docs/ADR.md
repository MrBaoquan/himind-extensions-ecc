# 决策记录

## 1. 为什么是独立仓库，而不是塞进 himind-extensions

上游是别人维护的库，技能数量会持续增长（当前 268 条，隔离 24 条）。把它放进主扩展仓库，会让主仓的提交历史被上游的节奏淹没，也让「谁改了什么」分不清。

独立仓库带来三件事：分发身份独立（`mrbaoquan/himind-extensions-ecc`）；上游漂移不会污染主仓；同步失败只影响这个仓库，删掉重来成本极低。

代价是多一个仓库要维护，以及依赖 `himind-extensions` 的校验工具——用 `go.mod` 的 `replace` 指向本地同层目录解决，不引入对私有模块代理的依赖。

## 2. A/B/C 三档，而不是「全都搬」

上游技能面向 Claude Code 之类宿主，写死了 `.claude/`、`CLAUDE.md` 这类路径和文件。

- **A 档**：正文与宿主无关，逐字搬。
- **B 档**：正文正确但引用了上游宿主路径，按 `upstream-policy.json` 的改写规则机械替换（`.claude/` → `.himind/`，`CLAUDE.md` → `AGENTS.md`）。改动属于「猜测」，所以 B 档变化不允许无人值守发版。
- **C 档**：依赖上游宿主壳层、脚本运行时或与 HiMind 自身冲突的技能，不搬，进隔离清单。

宁可少搬几条，也不搬进来一堆看起来能装、装完不好用的东西。

## 3. 生成必须是确定性的

生成过程是纯函数：同样的上游提交 + 同样的策略与元数据 → 同样的字节。生成时间、工具名这类字段在「没有实质变化」时沿用旧值。

这样 `probe` 才能用摘要直接判断要不要往下走，而不是靠人看 diff。没有这条，定时任务每天都会造出一个假的新版本。

## 4. 版本号用 `<上游 major>.<上游 minor>.<同步序号>`

Agent 比版本时只看前三段数字。上游版本带 `v` 前缀或 `-beta` 后缀时，直接搬会让两个不同版本比出相等的结果，自动更新就失效了。所以只取前两段，第三段是本仓库的同步序号，每次真实变化才 +1。

## 5. 元数据闸门：derived 不发，reviewed 才发

技能的显示名和说明，一开始是从 SKILL.md 里机械截出来的（`source: "derived"`）。这类文案没经过人眼，直接上市场就是拿用户体验赌运气：名字会被压到 18 字上限，说明会从句号后面断掉。

所以默认 `allow_derived=false`：只有 `manifests/metadata.json` 里标成 `source: "reviewed"` 的技能才会发布，其余写进 `held_for_metadata_review` 挂起。想让某条上架，改一个字段即可，不需要懂整条链。

首轮把 268 条全部人工读过一遍（见 17 节），现在仓库里没有 `derived` 条目；新技能从上游进来时仍会以 `derived` 入场，走同一道闸门。

校对过的文案也参与变更判断：`upstream.lock.json` 每条技能记了 `metadata_digest`。正文没动、只改了名称或说明时，只有这条技能涨版本，改完就能发出去；没记这个摘要，文案改了不涨版本，市场里永远显示旧的那一版。老锁文件没有这个字段，第一次跑只回填、不涨版本，避免几百个技能一起冒出「可更新」。

## 6. 隔离清单而不是报错退出

上游会不断引入带脚本、超大文件、或改了名字的技能。遇到这些直接让整条链失败，会导致「因为一条技能不合规，267 条都同步不了」。

正确做法是把它挑出来写进 `manifests/quarantine.json`，附上文件列表和原因，其余照常往下走。人只需要定期看这份清单，决定是排除、改造成插件，还是永久忽略。

## 7. 分发目标是仓库约束，不是命令参数

每条扩展在 `extensions.json` 里显式声明分发到工作台、GitHub 还是两者。发布步骤读这个约束，不让人在命令行临时决定。

理由：约束属于仓库的意图，应该跟着代码走、可复查、可回溯；命令参数只活在执行过一次的终端里。

## 8. 用工作流 + 定时计划闭环，而不是 GitHub Actions

同步要用到本地的东西：Go 工具链、`git`、`gh` 凭据、签名私钥和本地缓存。硬塞进 GitHub Actions 意味着把私钥搬上云、把依赖仓通过 token 拉进来，多出来的是攻击面，不是自动化。

所以闭环放在 Agent 侧：插件封装能力，工作流串起来，定时计划负责按天触发，任务中心负责留痕。拿本地已有的凭据跑，人不用介入。

## 9. 无人值守的授权边界

定时任务在没有人看着的时候跑，所以发布这一步被刻意做窄：

只允许「A 档变化 + 门禁全绿 + 元数据已校对」自动发版。B 档改写、技能删除或改名、上游许可证变化、门禁不过——全部停下等人。

判断依据写在 `upstream.lock.json` 和同步报告里，跑完能一眼看出这次是「其实没变」「自动发了」还是「卡住了、卡在哪」。

## 10. 启动入口显式声明工作区，而不是「留空就用当前目录」

`sync` 入口的 `requires` 是 `["workspace"]`，界面字段名是 `workspace_root`（`workflows/ecc-skill-sync/ui/workflow-view.json`）。

理由：这条链要拉上游源码、写生成结果、跑 Go 门禁，都必须落在一个明确的目录里。早先的写法是「不传就用当前工作区」，在手动跑的时候看起来很方便，但定时计划**没有「当前工作区」这个概念**——到点触发时缺工作区，会一路跑到插件步骤才失败，报出来的错还是插件内部的 `repo_root not resolved`，排查成本全落在人身上。

显式声明之后，缺工作区会在入口 preflight 阶段就被拒，错误指向入口参数本身。代价是手动跑必须选一次目录；对一条按天无人值守执行的链，这个代价换来的确定性是值得的。

## 11. 三类制品都要发，且发布顺序是硬约束

一次同步产出三种制品：插件 `com.mrbaoquan.ecc-skill-sync`、技能（每条一个包）、工作流 `com.mrbaoquan.workflow.ecc-skill-sync`。

它们必须按 `plugin → skill → workflow` 的顺序进索引，因为工作流的依赖里 pin 了插件的版本和制品摘要；插件没先进索引，工作流清单里的 pin 就解析不出来。

这条约束由 `internal/eccsync/publish.go` 的 `sortTargets` 固定，不靠调用方自觉。

## 12. 闭环的三段，各自都要有可复查的产物

「自动迁移」不是一条命令跑完就算数，它由三段组成，每段都要能独立复查：

| 段 | 谁执行 | 复查依据 |
| --- | --- | --- |
| 发布 | `publish` 能力 → GitHub Release | Release tag `workflow/com.mrbaoquan.workflow.ecc-skill-sync@1.0.4`，制品 sha256 记在 `dist/*.json` 与 `.himind/catalog.json` |
| 安装 | Agent 的 `extension.distribution.install` | 安装报告里的 `installed` 列表；profile 下 `installation.json` 的 `current_version` |
| 触发 | 定时计划 `ecc-skill-sync-daily`（`0 3 * * *`） | `schedule.list` 的 `last_run_id` / `last_status` / `next_run_at`，Task 中心能看到同一条 Run |

安装这一段的判定必须是「版本精确匹配」：早先的实现只比对扩展 id，于是本机装着 1.0.0 时去装 1.0.1 会被判成「已安装」直接跳过，报告显示 `state: ready` 但 `installed: []`。现在安装判定比对 id + 版本，旧版本会正常走升级路径（`versions` 保留旧版本用于回滚）。

## 13. 对齐事实随源码树落盘，`generate` 不再自己问一次 HEAD

定时计划第一次真触发时整条链在第三步失败，报的是「无法从上游版本 "" 推出制品版本」。真正的原因不是版本，是 `generate` 为了拿上游事实又打了一次 GitHub：

- 这一步本来只需要「probe 判定过的那份事实」，却被实现成「再问一次 HEAD 与 package.json」。本机出口到 `api.github.com` 是偶发 TLS 握手超时，这一问失败，当天整条同步就没了。
- 更隐蔽的问题是 HEAD 会在 `probe` 与 `generate` 之间移动。那时生成的制品既不属于 probe 判定过的提交，也不属于下一次 probe 的基线，「同一上游提交生成同一份字节」的确定性直接断掉。
- 版本读空时若继续往下走，错误会一路变形，最后在 `publish` 报成「无法从上游版本 "" 推出制品版本」，把真正的原因埋掉。

现在的分工是：`fetch` 取一次上游事实，原样写进源码树根的 `.ecc-upstream-facts.json`；`generate` 只读这棵树，不碰网络。`UpstreamFacts` 读不到版本就直接报错，不再返回空值往下传。碰到更早版本留下的、没有事实文件的缓存，退回用「目录名短 sha + 树里的 package.json + 锁文件」拼出来，并尝试用本地裸仓库把短 sha 补全。

收益是可量化的：一次同步从 3 次以上 GitHub 请求降到 2 次（都在 `probe`/`fetch`），且这三步都变成纯本地计算——定时任务里最容易抖的一段彻底消失。

## 14. 发布是能断点续跑的事务，不是一把梭

发布链路要连着打 GitHub 好几次（建 Release、传资产），中间任何一次抖动都会留下半成品。修之前有两种坏结局：

- 一次网络抖动就让当天整条链失败，人得第二天再看。
- 更糟的是「Release 已经建了、资产只传了一半」。这种中间态重跑时如果直接 `gh release create`，只会撞上 `a release with the same tag name already exists`——本来可以自愈的状态，变成了要人工清理的故障。

现在 `ensureRelease` 是「先查、再补、最后回读」：先看 tag 有没有 Release，没有才建；已经有就只补缺的资产（`--clobber`）；两个资产都在了才返回地址。索引只在回读确认之后才写——索引里的 `download_url` 指向的正是这两个资产，资产没传全就写索引，等于把「装不上」的东西挂到市场上。

判「Release 不存在」和「网络抖一下没查到」也是分开的：只有 `release not found` / `HTTP 404` 才算不存在，其余失败按可重试处理，避免把一次查询抖动误判成「还没发过」而重复建 Release。

底层共用一套有界重试（`internal/eccsync/retry.go`）：REST / raw / codeload 三类请求与所有 `gh` 调用统一走 `runWithRetry`，默认 5 次、退避按 base 翻倍并带正向抖动、单次等待上限 30 秒，只重试传输错误、5xx 与 429（4xx 重试没有意义，直接失败），用尽后在错误里标出「已重试 N 次」。Go 与 `gh` 都会把底层错误压成文本，所以判定按已知的抖动片段做小写匹配。

选择「有界重试 + 幂等补写」而不是「无限重试」或「失败就人工介入」：几十秒内自愈的抖动占绝大多数，连续五次都失败说明不是抖动，这时候把错误交给上层去看，比继续耗时间更值。

## 15. 命中缓存就不该联网，`probe` 的结论要交给 `fetch`

定时计划第一次真触发时，`probe` 已经问到了上游提交，`fetch` 却又去问了一遍。

根因是 `Fetch` 的实现顺序：先 `UpstreamFacts(policy, options.Commit)` 打 `api.github.com` 查提交、再读 `raw.githubusercontent.com` 拿版本，**之后**才检查本地缓存目录。顺序反了，缓存就永远是死代码——每一步都会先承受一次网络抖动，抖输就报 `E-S-FETCH`，本地明明躺着那棵树也用不上。

现在是两段式：

- `options.Commit` 非空且本地已有该提交的源码树（树里有 `skills` 目录）且事实可读，直接返回 `reused`，**零网络请求**；
- 否则才走 `resolveFetchFacts`。

没有显式提交时也不再无脑问 HEAD：`probe` 会把这次问到的提交、时间、版本写进 `.cache/ecc-sync/last-probe.json`（TTL 30 分钟，短 sha 视为无效），`fetch` 优先读它，读不到才真的打一次 `api.github.com`。

`probe` 自己也紧了：一次同步只问一次上游 HEAD；提交没变时版本直接沿用锁文件里的记录，不再白读一次 `package.json`；提交变了才读一次新版本，且读不到也不影响「变了」这个结论。

为什么 TTL 是 30 分钟而不是「一直有效」：定时计划每天跑一次，两个步骤之间相隔几秒；TTL 只用来覆盖「同一次运行内的交接」。留太久反而危险——间隔几小时后 `probe` 的结论已经过期，拿旧提交去 fetch 会把「该不该同步」判错。

## 16. 残留 Draft 按命名空间清扫，不靠「下次发同一个 tag 顺手清掉」

Draft 清扫原先只覆盖「本次要发的那个 tag」。这条路径有个死角：半成品是上一次发布卡在挂资产那一步留下的，正常情况下下次发同一个 tag 就顺手清掉了；**但只要期间版本号被手工涨过，旧 tag 永远不会再被发一次，那条半成品就永久留在仓库里**。这不是理论推演，是真实发生过的——插件 1.0.5 的 Draft 就因为版本号跳到 1.0.6 而成了孤儿。

现在清扫范围按 `extensions.json` 里的扩展 ID 精确圈定（`managedOwners`）：凡是 tag 归属到本仓库名下扩展、且还处于 Draft 状态的 Release，一次全清，与本次发不发得着它无关。判定不是「见到 Draft 就删」——`managedTag` 只认 `plugin/`、`skill/`、`workflow/` 三种前缀且 `@` 前非空，仓库里别人发的 Release 不在名单里，不会被碰。

清扫只在「本次确实有东西要发」时进行：上游没变时整条链在第一步就结束了，不会为了「顺便看两眼」去动网络。清掉的 id 会写进 `publish.cleaned_drafts`，跑完能复查这次到底清了什么。

## 17. 校对是三态机，基线只在「文案刚被人读过」时刷新

闸门只区分「有没有写元数据」是不够的。上游每天都在动，技能正文一改，之前读过的文案就可能不再对得上；而 `metadata.json` 里那条记录看起来仍然完好——它记不住「人是照着哪一版正文读的」。所以校对要记两件事：文案本身，以及读文案时的正文摘要。

于是有了三态，判据只有两个字段：

| 状态 | 判据 | 市场可见 |
| --- | --- | --- |
| `derived` | `metadata.json` 里这条不是 `source: "reviewed"` | 否 |
| `reviewed` | 人工校对过，且 `reviewed_digest` 与当前正文摘要一致 | 是 |
| `stale` | 人工校对过，但 `reviewed_digest` 与当前正文摘要不一致 | 是，并进入待重校队列 |

`stale` 不撤下市场：文案还没过时，只是正在过时的路上。下架对用户是倒退，对校对也没有帮助；要的是让人知道「这条该重读一遍」。

**基线为什么不能用 `source_digest`。** 用上游正文摘要当基线，上游一动就会被判成「刚刚重校过」，待重校标记永远不会亮——那这条链路就白写了。`reviewed_digest` 只在元数据摘要变化（也就是文案刚被人改写）时刷新成当前正文摘要；除此之外一动不动。

**队列为什么不落盘。** 待校对清单是算出来的：锁文件里的技能，减去已经是 `reviewed` 且未过期的，剩下的就是欠账。落一份 `review-queue.json` 就会和 `metadata.json` 抢「谁是真相」，而上游一直在动，两份真相只会越走越远。

两条命令把整件事做完整（CLI 与插件同源）：

- `review-queue`：`--status` / `--category` 收窄成一批，`--format markdown` 输出可直接读的清单，按「分类 → slug」排序——同分类里的技能说的是同一件事，连着读比跳着读快，也不容易两批写出互相打架的文案。每条同时列出上游原文与当前文案，校对的人不必回去翻源码。
- `review-apply`：读一份 `{slug: {name, description}}`，落进 `manifests/metadata.json`。**先全批校验、再整体写**：300 条里第 200 条名字超长就中途停下，人根本不知道自己读到哪儿了。校验用的是与生成同一组硬约束（名称 ≤18 字、说明 ≤120 字），落得进库的文案就一定生成得出来。

校对时会清掉 `note`（推导留痕）并写上 `reviewed_at`。留着 `note` 会让下一个人以为这条还没读过。

## 18. 分发策略独立成仓库内文件，只约束上游技能

「这个方向的技能团队用不到」和「不要把这类技能搬进仓库」是两件事，最早实现里只有后者。

想让某类技能不再往外发，唯一办法是把它从 `upstream-policy.json` 的搬运范围里删掉。后果比「少发几条」严重：技能从仓库里消失，已经装了的用户既看不到也回不来；上游再改正文也不会有人知道；哪天改主意想恢复，策略文件里没有留痕，只能凭记忆把条目重新加回去再跑一次全量生成——几百条技能的版本号因此集体跳一次。

现在两份策略并排放在仓库根，各管一段：`upstream-policy.json` 管「搬不搬进来」，`dispatch-policy.json` 管「搬进来的发不发」。前者决定仓库里有什么，后者决定市场里更新什么。

**判定是三档，越具体的先判**：单条技能 > 上游模块 > HiMind 分类。三档同时存在是有用的——按分类排掉一整片（例如「测试质量」里大半是上游内部流程），按上游模块更精确地排掉其中一块（例如 `framework-language` 里只排 Kotlin 系），偶尔单条技能需要单独豁免。判定顺序必须固定，否则同一条技能会因为先看分类还是先看模块而得出两种结论。

**缺省是全放行，不做反向白名单。** 文件不存在、三个集合为空，都等于「全部参与分发」。白名单的失败模式是灾难性的：策略文件丢一次、字段写错一次，市场里几百条技能同时停更，而且没人看得出来——「没变化」和「被排掉了」在发布报告里长得一样。黑名单最坏情况只是少排几条。

文件不存在时按空策略处理，不是按错误处理：老仓库升级上来时还没有这份文件，报错会让整条同步链在安装的第一天就停摆。文件存在但 `schema_version` 对不上则报错——那说明有人写了本工具读不懂的策略，静默忽略等于悄悄改了分发范围。

**写错要拦在落盘前。** 模块名、分类名、技能 slug 任一个写错，都不会有语义上的报错：那条规则只是永远匹配不上，结果和没写一样。所以保存策略之前先用 `manifests/modules.json` 与锁文件校验一遍，一处不对就整份不落盘。界面比命令行更需要这道闸门——命令行至少是手打的，界面里点错一个开关不该悄悄变成「什么都没排掉」。

**被排掉不等于下架。** 已经在线上的旧版本保持可用，只是不再产生新版本。下架对用户是倒退，对分发也没有帮助：用户装好的东西不会因为市场删了条目就消失，只会变成一个装得上、更新不了的孤儿。

**跳过必须报数。** `PublishResult` 加了 `excluded` 计数与 `excluded_items` 明细（slug、ID、版本、模块、分类、命中规则、原因）。定时任务每天自动跑，如果被策略挡下的技能不写进报告，「少发了几条」这件事就没有任何地方能看出来。明细里的 `rule` 与 `keyword` 决定了这条是分类、模块还是单条技能挡下的——策略是按类生效的，一条技能消失时必须能立刻回溯到是哪一条规则。跳过清单按 slug 排序：锁文件是 map，遍历顺序随机，不排序的话同一份策略每次跑出来的报告顺序都不一样，两次运行之间没法比对。

**跳过清单要落成文件，不能只在运行记录里。** 发布环节一开始只把 `excluded` 与 `excluded_items` 放进能力应答，`generate` 才写报告。后果是无人值守的那条路上什么都没有：定时任务跑了三个月，想知道「这条技能是从哪一天开始不更新的」，只能去翻运行记录里那条已经被挤到很后面的步骤输出。现在 `ecc.sync.publish` 与 `ecc.sync.generate` 一样落报告（`.cache/ecc-sync/reports/<UTC 时间戳>-publish.json`），上游锚点取自锁文件，两份报告对得上：生成报告说对齐到哪个提交，发布报告说在这个提交上谁发了、谁被哪条规则挡下。

报告契约只有一个（`ecc_sync_report`），靠 `kind` 分叉：`generate` 要求 `upstream` + `result`，`publish` 要求 `publish` 段（含 `excluded` 与 `excluded_items` 的形状）。分成两种 artifact 类型也能做，但那要在工作流包里多声明一份 artifact，而这两份报告回答的本来就是同一个问题——「这次同步到底做了什么」。

**报告写入只能有一份实现。** 同一条链路上有三个入口：命令行（人手动发版时就走的这条）、插件能力（Agent 侧与定时任务走的这条）、工作流步骤（把能力串起来的这条）。最早报告只写在插件里，于是命令行发版不留任何凭据——而真实发版恰恰经常是人在命令行里跑的。现在 `internal/eccsync` 出 `WriteRunReport` / `GenerateReport` / `PublishReport`，三个入口调用同一份代码，谁跑都留痕，报告的形状也不会各自漂移。

**空锚点不算锚点。** `LoadLock` 在锁文件缺失时返回空锁而不是错误，早期实现会把 `upstream: {}` 原样写进发布报告：既过不了契约里 `repository` / `commit` 的必填校验，又会在复盘时假装自己知道对齐到哪个上游提交。现在只有拿到非空的 `commit` 才写这一段，其余情况报告照写、少一块锚点。

**同一秒的两份报告不能互相覆盖。** 文件名精确到秒，于是「真发一次、紧接着干跑一次复核」这种再正常不过的动作会让第二份把第一份顶掉——被顶掉的恰好是那次真发布的唯一凭据。现在撞名时加序号（`…-publish-2.json`），命名习惯不变。

**插件与工作流不参与这套策略。** 它们是本仓库自己写的扩展，要停发改的是自己的分发落点；混在一起的话，哪天误排一个分类，工具链自己就跟着停更了，连「怎么把自己的更新发出去」都做不到。所以策略只在挑上游技能这一步生效，插件与工作流照常进发布队列。

**策略放在仓库里，不放插件私有目录。** 它是内容事实：谁不参与分发、为什么，要能进版本控制、能被评审、能被回滚。放在私有目录的话，策略会跟着机器走——定时任务跑在哪个工作区就读哪一份文件，同一份仓库在两台机器上会分出两种分发行为。

插件视图「分发管理」（`ecc-skill-sync.dispatch`）与 CLI 同源，走的都是 `ecc.sync.distribution`（只读状态）与 `ecc.sync.dispatch_policy_save`（整份写回）。保存是整份覆盖而不是增量叠加：界面手里本来就是完整策略，增量接口会让「取消排除」变成一次语义含糊的删除。

## 19. 发布前先把提交推到远端，tag 用 `--target` 钉死

`gh release create <tag>` 不指定目标时，tag 建在默认分支当前的 HEAD 上；而这个仓库发布时记的来源提交取自本地 `git rev-parse HEAD`。两者本该是同一个提交，但只在「这次提交已经推上去」时才成立。1.1.1~1.1.5 五个版本就是这么错的：本地提交先发版、后推送，五个 tag 全部落在 1.1.0 那个提交上。

错得隐蔽，是因为没有任何一步会当场发现。Release 的资产是本地打的、内容是新的，装机路径也只按资产下载，所以市场、安装、升级全都正常；只有「按 tag 取源码」这条平时没人走的路拿到旧代码。唯一留痕的地方是发布清单里的 `source_commit`——它是发布当时本地 HEAD 的完整提交号，也是这次重指历史 tag 的唯一依据。按 `plugin.json` 里的版本号去猜 tag 该落在哪个提交上会猜错：版本号先涨、索引提交随后补，是这条链固有的节奏。

修复分两处，缺一不可：

- **建 Release 时显式 `--target <来源提交>`。** 只加护栏不够——来源提交本身可能是个远端不认得的提交，那一步得直接失败，而不是退回默认分支。来源提交读不到时宁可不带这个参数让 gh 报错，也不拼一个空 `--target`：那时制品已经打完、签名已经做完，白跑一轮。
- **真发布前问一次目标仓库有没有这个提交，没有就停。** 问的是发布目标仓库（`--repository` 指定的那个），不是本地 `origin`：本地远端引用可能过期，也验证不了目标仓库。只有 404 / Not Found 才硬停；限流、网络抖动只是这次问不出来，交给 gh 那一步去报——把「问不出来」当成「没推」，会让无人值守的定时任务在自己家网络打嗝时整条停住。干跑不写 tag，也就不查。

连带把顺序写死：**提交 → 推送 → 发布 → 补索引提交**。历史 tag 已按发布清单里的 `source_commit` 重新指向（移动 tag ref，Release 与资产原地不动，下载地址不变，已装 1.1.5 的机器不受影响）。

## 20. 一次同步发一条批次 Release，命名取上游版本加同步序号

技能逐件发的时候，一次同步往仓库里塞 268 条 Release。首页于是退化成版本流水账：翻不到「这一批是什么」，回收也只能逐条做，而逐条回收必然落后于逐条发布。现在技能整批发成一条批次 Release，插件与工作流仍然一件一条——它们的版本是人工涨的，本来就不成批。

**归类的主轴是上游版本，唯一性靠本仓库的同步序号。** 批次版本取「上游 `package.json` 的 major.minor.patch + 同步序号」，`batch/2.2.2.3` 读作「上游 2.2.2 的第 3 次同步」：翻 Release 列表时先看对应上游哪一版，再看这是第几次搬过来。但上游版本不能单独当名字——上游按自己的节奏发版、同步按周跑，同一个上游版本会被同步很多轮（2.2.2 已经同步过三轮），第二轮起 tag 就没名字可用。上游的 Release tag 更不能直接用：它与 `package.json` 差一档（tag 停在 `v2.2.1` 时 `package.json` 已经写着 2.2.2），且同样一轮一个。上游版本与提交另外写进批次清单 `batch@<version>.json` 留档，溯源不靠 tag。

批次号只负责在批次之间排序（回收按它挑保留窗口），不负责盖住成员版本：成员版本走的是另一套推导（上游 major.minor + 同步序号），两者不共享序数，硬取大值只会让批次名在不同轮次里换格式。两套版本都按数字段比较，同步序号涨到两位数也不会把「第 10 次」排到「第 9 次」前面。

**批次是容器，不是把一批内容糊成一张表。** 每件技能照旧各自打包、各自签名、各自写发布清单与索引；只有「挂在哪条 Release 上」变成批次 tag，成员发布清单里的 tag 随之写批次 tag，装机器按同一条 Release 取资产，路径反查（`github:<tag>:<artifact>`）与依赖 pin 都自洽。批次清单的成员按「类型 + ID」排序，同一批内容重复发布时清单逐字节一致，否则「这批跟上一批有没有差别」只能靠人眼比对 JSON 顺序。

**建 Release 与挂资产拆成两次调用。** 一条批次 Release 的资产是五百多个，全塞进 `gh release create` 会撞上 Windows 32767 字符的命令行上限，而那时制品已打好包、签名已做完，白跑一轮。Release 建出来到资产挂满之间索引还没有指向它，市场里看不到半成品；回读确认资产齐全之后才写索引。

**回收按整批做，批次有自己的保留窗口。** 一批对应一次同步，成员是好几百件技能，回收粒度落到成员身上就会出现「这一批里有两件还要留」，而那不是一个能表达的诉求。批次因此单独计 `keep_versions.batch`，整体进出。批次 tag 里没有扩展 ID，认归属只能靠「本仓库自己发过、并记进了索引」，没进过索引的批次 tag 一律不动——那可能是别人在同一个仓库里发的；被依赖 pin 钉住的批次同样不回收，删掉它，已发布的工作流就指向一条不存在的 Release。
